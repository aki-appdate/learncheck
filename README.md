# LearnCheck — 研修の理解度チェック

[![CI](https://github.com/aki-appdate/learncheck/actions/workflows/ci.yml/badge.svg)](https://github.com/aki-appdate/learncheck/actions/workflows/ci.yml)

研修資料から**AIが確認テストの案を作り**、研修担当が**1問ずつ確認してから公開**。受講結果から**伝わっていない所とフォロー研修の案**を出すWebアプリです。
社内研修の「やりっぱなし（受けたかどうかしか分からない）」を減らすことを目的に、Claude Code を使って設計・実装しました。

> デモ版です。会社・人名・部署・研修資料などのデータはすべて架空です。ログイン不要で、誰でも試せます。

## 解決したい課題

| 研修の現場の困りごと | LearnCheck でやること |
|---|---|
| 確認テストを作るのに時間がかかり、研修が「受けっぱなし」になる | 資料を選ぶか貼り付けて、問題数と難しさを選ぶだけで、AIが4択問題・解説・根拠の引用文を作る |
| AIに問題を作らせると、資料にないことを混ぜてしまう | 引用文が資料に本当にあるかをプログラムで確かめ、見つからない問題は「根拠を確認できません」と目立たせる。引用文が正解と関係なさそうなときも注意を出す。人が確認した問題だけで公開 |
| 受講結果が点数だけで、どこが伝わっていないか分からない | 問題ごとの正答率・よく選ばれた誤答・部署別の弱点（部署×問題で全体より大きく低い所も）を集計し、AIが根拠の問題つきでフォロー研修の案を出す |

## 主な機能

**研修担当：テストを作る（/admin）**
- 研修資料を選ぶ（デモ用に4本）か、自分の資料を貼り付ける（200〜6,000字）
- 問題数（5・8・10問）と難しさ（やさしい・ふつう・むずかしい）を選んで「AIで確認テストを作る」
- 資料ごとに受講の対象を決めている（例：自社商材の資料は営業1課・営業2課だけ。ほかの資料は全員）
- 問題ごとに、引用文が資料の中にあるかを自動で確認し、該当箇所に印をつけて表示。見つからない問題は赤で警告し、そのままでは採用できない
- 引用文は資料にあっても、正解の選択肢の言葉が引用文に1つも出てこないときは「注意：正解の根拠になっているか確認してください」と出す（採用は止めない）
- 選択肢の重複・空欄、正解の位置の偏り（例：半分以上が「A」）、同じ問題文も自動で知らせる
- 1問ずつ「採用／直す／捨てる」を選ぶ。直すときも、根拠の文が資料にあるかをその場で確認。実際に書き換えた問題には「人が修正」の印が残る（何も変えずに「直して採用」を押したときは付かない）
- 「別の問題で作り直す」で、同じ資料・問題数・難しさのまま、別の箇所や聞き方の案に作り直せる（確認の状態は消える）
- 未確認の問題が残っている・採用が3問未満・採用した問題に不備がある間は公開できない。公開したテストは書き換えない

**受講者：テストを受ける（/learn）**
- 受講者を選んで受験（自分が対象のテストだけが出る）。1問答えるごとに正誤・解説・資料の該当箇所を表示
- 最後に点数と間違えた問題の正解を表示し、結果を保存。前回の点数と受講回数が一覧に出る

**研修担当：結果を見る（/results）**
- 平均点・受講済み人数・満点の人数・間違いが多い問題（正答率60%未満）の数
- 問題ごとの正答率。押すと選択肢ごとに何人が選んだかと、根拠の箇所を表示（まだ誰も受けていないテストは「—」）
- よく選ばれた誤答、部署別の平均点と一番間違いが多い問題、受講者ごとの点数と未受講者
- 「AIによるフォロー研修の提案」：気づき最大3つと次にできるフォロー。**気づきごとに根拠の問題を開いて確かめられる**。全体の正答率はそれほど低くなくても、特定の部署だけ大きく低い問題（例：カスタマーサポートの3人が第10問を全員間違えた）も取り上げる

## AIの使い方で気をつけたこと

1. **人が最後に決める**：AIが作った問題は下書きです。研修担当が1問ずつ確認し、採用した問題だけで公開します。フォロー研修の案も「参考情報」として表示します。
2. **作り話を防ぐ**：AIには根拠となる資料の文を「一字一句そのまま」書かせ、その文が資料の中にあるかをプログラムで照らし合わせます。同じとみなすのは書き方の揺れ（空白・改行、全角／半角、『』と「」、数字の範囲の「〜」「～」「-」「－」「ー」）だけで、言い換えは認めません（[src/lib/quote.ts](src/lib/quote.ts)）。引用文が資料にあっても正解の言葉が出てこない場合は、関係のない文を引いている可能性があるので注意を出します（[src/lib/quality.ts](src/lib/quality.ts)。言葉の一致を見るだけなので目安です）。フォロー研修の案では、AIが挙げた根拠の問題IDが実在するかを確かめ、根拠のない気づきは捨てます。
3. **返答の形を固定する**：zod で定義した型から JSON Schema を作って Gemini に渡し（構造化出力）、受け取った値も同じ zod で検証します。形が違えば使いません。
4. **止まらない**：AIが使えないとき（未設定・無料枠の上限・通信エラー・返答の形の不正）は、ルールベースの「見本の返答」に自動で切り替えます（通信エラーと形の不正は、画面に出す案内を分けています）。見本の返答も、資料の文から実際に問題を作ります。
   - 空欄の問題：大事そうな文の語句を空欄にし、資料の別の文に出てくる同じ種類の語句や、正解に近い数字を誤答にする。「お（　）」や「情報（　）担当」のような言葉の切れ端・送りがなの途中・かっこの中は空欄にせず、資料で並べて書かれた言葉など、入れても正しく読めてしまう誤答は使わない。数字の誤答は、正解より大きいもの・小さいものの数を乱数（種を固定）で決め、並べたときに正解がいつも同じ順位にならないようにする。「4つのうち（　）種類以上」のように、問題文を数えれば上限が分かる数を超える誤答は出さない
   - きまりの問題：「〜してはいけません」「必ず〜」のような文を選び、ほかのきまりの文を逆の意味に書き換えたものを誤答にして「正しいもの」（または「合わないもの」）を選ばせる。「〜てもかまいません」のような許可の形の選択肢だけが浮いて、言い回しで答えが分かる問題は避ける（「合わないもの」で答えだけが許可の形になる問題は0件）。語尾の種類（「〜ください／〜てはいけません／〜禁止です」・許可の形・ふつうの言い方）が4つの中で答えだけになる組み合わせも作らない。「きまりの言い方で終わる選択肢が1つだけなら、それを選ぶ」で解くと、「正しいもの」330問で当たり0問・外れ11問（直す前は206問で当たり85問・外れ29問）。ただし「合わないもの」では、きまりの言い方で終わる選択肢が1つだけの問題が518問中121問（23%）あり、その1つは答えではない。「浮いた1つを外す」で4択が3択になる手がかりは残っている（見本資料4本と貼り付けた資料2本×難しさ3×5・8・10問×作り直し4回で集計）
   - 数字の問題は、実際にできた問題数のおよそ半分まで。数字の誤答は「9時から（　）まで」なら9時より後・24時まで、「（　）を組み合わせます」なら2以上にする。解説は根拠の文と資料の見出しを引いて書く
   - 作れる問題の数：1つの文はテスト全体で1回しか使わないので、見本資料でも10問を選ぶと7〜9問になる（個人情報7〜8・セキュリティ8〜9・ハラスメント8・自社商材9問。5問・8問なら指定どおり）。作成画面では、作る前に「この資料なら、見本の返答で作れるのは◯問ほどです」と出す
   - よく似た文がくり返す長い資料では、文の組み合わせを探すのに時間がかかるので、2秒で打ち切ってそれまでに作れた一番多いものを使う（作る前の見積もりは、入力が止まってから0.3秒まで）。ふつうの資料は数ミリ秒で終わる
   - 難しさで変えるもの：やさしい＝きまりの問題は「正しいもの」を選ぶ形が多め・数字の誤答の幅が広い。むずかしい＝「合わないもの」が多め・誤答は同じ項目の文から選び、数字は資料の別の数字を混ぜる（[src/lib/labels.ts](src/lib/labels.ts) の説明を、作成画面とAIへの指示文の両方で使う）。穴埋めの問題の数は、資料にある数字・言葉の数で決まるので、難しさではほとんど変わらない（見本資料4本・8問の合計で、やさしい9・ふつう8・むずかしい8問）。きまりの問題の「正しいもの／合わないもの」の数は、見本資料4本×作り直し4回の合計で、やさしい 5問 51／0・8問 65／28・10問 57／41、ふつう 28／24・41／53・46／53、むずかしい 16／40・21／75・5／96。資料ごとに見ると、10問では数をそろえるために「合わないもの」だけになることもある（例：自社商材・10問・やさしいは9問で、きまりの問題5問がすべて「合わないもの」）。作成画面にもそう注記している。短い資料では作れる問題の種類が限られるので、違いは小さくなる

   **見本資料と貼り付けた資料の違い（正直に書いておきます）**：文を逆の意味に書き換える汎用の規則（「〜してはいけません」→「〜します」など）は、文の形によっては不自然な日本語になります。そこで見本資料4本には、研修担当がそのまま出題できる言い回しの誤答の候補を、資料ごとに人の手で用意しています（[src/lib/materials.ts](src/lib/materials.ts) の `distractorHints`）。貼り付けた資料では、この候補はなく汎用の規則だけを使い、自然に書き換えられない文は誤答に使いません。そのため貼り付けた資料では、見本資料より作れる問題が少なくなります（400字ほどの資料で3〜4問）。作成画面では、作る前に「この資料なら◯問ほど」と知らせます。

   引用文は資料の文をそのまま使うので、必ず資料の中にあります。ルールで作るため、AIほど自然な問題にならないこともあります（そのためにも人の確認を通します）。画面上部の表示で、どちらが動いたか分かります。
5. **使いすぎを防ぐ**：Firebase App Check でこのサイト以外からの呼び出しを防ぎます。画面側では、ブラウザごとに1日のAI利用回数の目安（20回）を設けています。これはブラウザの保存領域で数えるだけの目安で、本当の上限ではありません。公開して使う場合は、Firebase AI Logic 側でも利用者ごとの回数の上限（レート制限）を設定する必要があります。

## 技術構成

| 分野 | 使ったもの |
|---|---|
| 画面 | Next.js 16（App Router）/ React 19 / TypeScript / Tailwind CSS 4 |
| データ保存 | Cloud Firestore（匿名認証で一人ずつ分離）。未設定時はブラウザの localStorage |
| AI | Firebase AI Logic + Gemini（Gemini Developer API の無料枠・Spark プラン） |
| セキュリティ | Firestore セキュリティルール（[firestore.rules](firestore.rules)：自分のデータだけ読み書きでき、項目の名前・型・文字数や件数の上限を確かめる。配列の中身1つずつまでは確かめられない）、App Check（reCAPTCHA v3） |
| 品質 | Vitest（単体テスト）、ESLint、GitHub Actions の設定（lint・型・テスト・ビルド） |

```
src/
├─ app/                 画面（/ 紹介、/admin テストを作る、/learn テストを受ける、/results 結果を見る）
├─ components/          画面の部品
└─ lib/
   ├─ ai/               AI呼び出し（gemini.ts）、指示文（prompts.ts）、見本の返答（sample.ts）
   ├─ store/            保存先（Firestore と localStorage を同じ窓口で切り替え）
   ├─ quote.ts          引用文が資料の中にあるかの確認
   ├─ quality.ts        問題の自動チェック（重複・正解の偏り・正解と根拠の文のずれ・公開できるか）
   ├─ analytics.ts      結果画面の数字の計算（採点・正答率・誤答・部署別・部署×問題）
   ├─ schemas.ts        AIの返答の型（zod）
   ├─ materials.ts      架空の研修資料（4本）
   └─ seed.ts           架空のデモデータ（受講者14名・公開済みテスト2本・受講結果）
```

### データの持ち方の工夫

デモデータ（受講者14名・公開済みテスト2本・その受講結果・下書きの例1本）は、乱数の種を固定した関数で毎回同じものを作れます。
そのため Firestore には「お試しを始めた日時」と「利用者が作った・直したテスト」「利用者が受けた結果」だけを保存し、書き込み回数を最小限にしています（無料枠で運用するため）。

結果画面が分かりやすくなるよう、デモデータには「漏えいに気づいたら、原因を調べてから報告する」という誤答に人が集まる問題や、部署によって間違いが多い問題（カスタマーサポートの3人だけが個人情報テストの第10問を全員間違えている、など）を仕込んでいます。少人数でも狙った傾向が崩れないよう、問題ごとに乱数を受講者へ均等に散らして配っています。
受講日は平日、時刻は 9:00〜18:00 の決まった時刻にしていて、開いた時刻によって変わりません。何人かは同じテストを2回受けています（集計は最新の結果）。公開済みのデモのテストは、AIではなく人が書いた問題です。

## 手元で動かす

```bash
npm install
npm run dev        # http://localhost:3842
npm run check      # lint・型チェック・テスト
```

Firebase を使う場合は `.env.example` を `.env.local` にコピーして値を入れます。空のままでも、ブラウザ内保存＋見本の返答で全機能を試せます。

## 分かっている小さな課題

- 同じ資料から作ったテストは、同じ名前になります。結果画面の「見るテスト」では、公開した日時を名前の前に出して見分けています（名前は公開前に書き換えられます）。
- 見本資料で10問を頼むと7〜9問になること、「合わないもの」の約23%で語尾から1つ消せることは、上の「AIの使い方で気をつけたこと」に書いたとおりです。
- Gemini と Firestore につないだ状態での動作は、Firebase のプロジェクトを作ってから確かめます（今は見本の返答とブラウザ内の保存で確かめています）。

## 開発の進め方

- 設計・仕様決め・動作確認は筆者が行い、実装は Claude Code に任せています。プロジェクトのルールは [CLAUDE.md](CLAUDE.md) にまとめています。
- AIが書いたコードは、テスト・型チェック・ブラウザでの操作確認（スマホ幅を含む）の3つで確かめています。
